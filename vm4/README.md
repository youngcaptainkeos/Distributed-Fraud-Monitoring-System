# VM4: Dashboard & Observability

VM4 is responsible for the interactive fraud monitoring dashboard, alert investigation workflows, and visualization of transaction processing results.

The dashboard is built using **Streamlit**, **Pandas**, and **Plotly**. It supports both a demonstration mode using the supplied ground-truth datasets and a live mode that queries Apache Iceberg tables.

---

## 1. Responsibilities

### 1.1 Spark Worker 2

VM4 is designed to operate as the second Spark Worker in the distributed architecture.

It registers with the Spark Master running on VM2:

```bash
$SPARK_HOME/sbin/start-worker.sh spark://<VM2_PRIVATE_IP>:7077
```

Worker registration can be verified through the Spark Master Web UI:

```text
http://<VM2_PRIVATE_IP>:8080
```

The worker provides additional distributed processing capacity to the Spark cluster.

### 1.2 Streamlit Monitoring Dashboard

The dashboard source code is located in:

```text
vm4/dashboard/
├── app.py
├── iceberg_source.py
└── start_sql_server.sh
```

The dashboard provides an interactive interface for monitoring transaction decisions and investigating fraud alerts.

### 1.3 Alert Investigation

The investigation interface provides:

- Plain-language explanations of triggered fraud rules.
- Triggering transaction details.
- Source account and destination account information.
- Recent transaction history associated with the source account.
- Alert-level details for investigating suspicious activity.

## 2. Dashboard Features

### 2.1 Global Filters

Users can filter dashboard data using:

- Time range.
- Source account ID.
- Fraud rule.

These filters help narrow down transaction activity and investigate specific suspicious accounts.

### 2.2 Key Performance Indicators

The dashboard displays important monitoring metrics, including:

- Total transactions.
- Total fraud alerts.
- Number of flagged accounts.
- Transaction and alert activity.

### 2.3 Visualizations

Plotly visualizations provide insights into:

- Alerts grouped by fraud detection rule.
- Transaction volume over time.
- Alert volume over time.
- Distribution of transaction decisions.

### 2.4 Data Tables

The dashboard provides tabular views of:

- Transaction decisions.
- Generated fraud alerts.
- Flagged accounts.
- Alert investigation details.

### 2.5 Alert Drilldown

Selecting an alert allows investigators to inspect:

- The rule responsible for the alert.
- The explanation generated by the fraud detection engine.
- The triggering transaction.
- The associated source account.
- The account's most recent 20 transactions, ordered by event time.

## 3. Environment Setup

Run the following commands from the repository root.

### 3.1 Create a Python Virtual Environment

```bash
python3 -m venv .venv
```

Activate it:

```bash
source .venv/bin/activate
```

If a virtual environment already exists, activate it instead of recreating it.

### 3.2 Install Dependencies

```bash
pip install -r requirements.txt
```

The project dependencies include:

- Pandas
- PyArrow
- Streamlit
- Plotly
- PyYAML
- Pytest

## 4. Running the Dashboard

From the repository root, execute:

```bash
streamlit run vm4/dashboard/app.py --server.port 8501
```

Once Streamlit starts, open the following address:

```text
http://localhost:8501
```

For access from another machine, use the dashboard host's reachable IP address and ensure the configured port is accessible.

## 5. Dashboard Data Sources

The dashboard supports two data-source modes.

### 5.1 DEMO Mode

DEMO mode uses the supplied ground-truth CSV datasets:

```text
data/
├── transactions.csv
├── ground_truth_transaction_decisions.csv
└── ground_truth_account_risk_alerts.csv
```

This mode:

- Works without a running Kafka or Spark streaming pipeline.
- Uses the supplied transaction decisions and alert datasets.
- Allows the dashboard interface and investigation workflows to be demonstrated.
- Is selected by default.

DEMO mode is useful for development, interface validation, and demonstrations.

### 5.2 LIVE Mode

LIVE mode retrieves data from Apache Iceberg tables through the SQL connection layer.

The expected run-specific tables are:

- `transaction_decisions_runN`
- `account_risk_alerts_runN`

LIVE mode requires:

1. HDFS to be running and accessible.
2. The appropriate Iceberg warehouse and catalog configuration.
3. The relevant Iceberg tables to have been created and populated.
4. The Spark SQL Thrift Server to be available.
5. Correct connection settings in `iceberg_source.py`.

If these requirements are not met, the dashboard may be unable to load live data.

## 6. Spark SQL Thrift Server

The dashboard's Iceberg connector communicates with the Spark SQL Thrift Server.

The startup script is:

```text
vm4/dashboard/start_sql_server.sh
```

Start the server using:

```bash
bash vm4/dashboard/start_sql_server.sh
```

The launcher supports environment-based configuration for:

- `SPARK_HOME`
- `HADOOP_HOME`
- `HADOOP_CONF_DIR`
- `HDFS_DEFAULT_FS`
- `HDFS_WAREHOUSE`
- `SPARK_LOCAL_IP`

For example, when HDFS is hosted at a non-default address:

```bash
export HDFS_DEFAULT_FS=hdfs://<VM3_PRIVATE_IP>:9000
```

The default Thrift Server JDBC endpoint is:

```text
jdbc:hive2://127.0.0.1:10000/default
```

The Thrift Server is configured to bind to localhost by default.

## 9. Deployment Architecture Note

VM4 represents a logical role in the four-VM project architecture.

In the intended deployment, VM4 hosts Spark Worker 2 and the Streamlit dashboard.

During development and testing, VM4 dashboard components may share a physical machine with VM3 HDFS storage and verification components.

The dashboard can therefore be tested independently in DEMO mode even when the other distributed machines are unavailable.
